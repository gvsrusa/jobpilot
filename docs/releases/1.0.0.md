# JobPilot AI 1.0.0

Stable open-source distribution. Status: not published. Installers are signed only when the project's certificates exist; none exist yet, so builds are unsigned. This is a personal, non-commercial app. Release 1.0 adds no apply capability: the security controls of 0.6 hold unchanged in every mode, the Claude Code apply mode included.

Rows marked `PENDING-T8` need the real release (signed installers, an update delivered from a release candidate, Windows update) and are filled by the controller in Task 8. Nothing in this note was written from a run that did not happen.

## What was built

- **Verified auto-update.** Status has **Check for updates** and **Install and restart**. The update is verified (minisign) against the public key pinned in `tauri.conf.json`; the endpoint is a GitHub URL with no runtime override. The launch check is opt-in (`updates.check_on_launch`, off by default), so the app makes no network call until you ask for one or turn it on. An install is refused while the emergency pause is set or an apply run is active, whether Claude Code, Copilot, or autonomous (`update_blocked_by_run`), and run starts are held off while an install is under way. Audit rows: `update_installed`, `update_install_failed`.
- **Key rotation.** Generate a new pair with `pnpm tauri signer generate`, replace `plugins.updater.pubkey`, and set the repository secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. An installed copy updates only to builds signed by the key it ships with, so a rotation needs a bridge release signed by the old key. See [development](../development.md#releasing).
- **A release workflow** (`.github/workflows/release.yml`). Pushing a `v*` tag builds a draft release with the `.dmg` (arm64 and x64), the `.msi`, the NSIS `.exe`, the updater `.sig` files, and `latest.json`. It signs and notarizes macOS when the `APPLE_*` secrets exist, signs Windows with Authenticode when `WINDOWS_CERTIFICATE` exists, and otherwise builds unsigned; the release body is one neutral text for all platforms (signed only where the certificates exist; see the README), because the platform jobs share one release. A macOS build with a certificate but no notarization credentials is signed and not notarized. A manual run (`workflow_dispatch`) is a dry run that builds without releasing. Every action is pinned to a commit SHA.
- **Supply-chain gates.** `deny.toml` and a `supply-chain` CI job: `cargo-deny`, and `pnpm audit --prod --audit-level high`.
- **A security review** ([review-1.0.md](../security/review-1.0.md)): every FR-12 requirement and mitigation M-01 to M-40 read against the code, with eight findings (S-1 to S-8), no critical one, and an outcome for each. Fixes include S-1 (a restored backup cannot choose which program runs as `claude`), S-2 (`browser_click` is one plain left click), S-3 in part (actions pinned, certificate scoped), S-4 (the webview capability narrowed), S-6 (a restore takes no path from the webview), S-7 (the data root created user-only), and S-8 (register drift).
- **Upgrade tests from every release**: databases at schemas 1, 5, 11, 12, 15, and 17 migrate to the current schema.
- **Public docs**: [SECURITY.md](../../SECURITY.md) (GitHub private advisories; 1.0.x supported), a README with an install section, an update section, and an index of every published doc, a releasing section in [development](../development.md#releasing), and D3 superseded for 1.0 in the [policy register](../policy-register.md).
- No migration. Schema version 17. Version 1.0.0.

## Known issues

- **Signing is pending certificates.** Until the Apple and Windows certificates exist, installers are unsigned: expect Gatekeeper and SmartScreen warnings (see the README). An ad-hoc macOS build has a new code identity each time, so keychain prompts can appear after an update.
- **S-3 residual.** The updater signing key is in the environment of the `tauri-action` build steps, because that action signs the updater artifacts while it builds. The action and the `beforeBuildCommand` it runs are therefore in reach of the key. The actions are pinned, but the build is trusted.
- **S-5 residual.** Some consequential acts (starting a Claude Code run with no sealed answers, ending a stop, changing the launch check) need only an IPC call, with no native confirmation. Each needs script running in the webview, and none was found: the CSP allows no inline or remote script and the frontend has no HTML sink.
- **The 0.6 known issues still apply**, including word-list stop detection, unchecked choices under ordinary questions, and the site-restriction risk the owner accepted. See [release 0.6.0](0.6.0.md#known-issues) and the [threat model](../security/threat-model.md#11-residual-risks).

## Not exercised

- A signed installer, a notarized build, and a real update delivered by a published release (all PENDING-T8).
- A real site, in any form, and the Windows runtime paths listed in the 0.6 note.

## Upgrading

Open a 0.6 database with 1.0 and the schema is unchanged (version 17); no migration runs. An older database upgrades through the usual path, with `backups/pre-migrate-<schema>-<stamp>/` written first; restoring that folder returns the earlier data. There is no down migration.

A restore keeps the live `ai.claude_path`, `ai.gemini_path`, `ai.codex_path`, `ai.ollama_url`, and `updates.check_on_launch` settings (S-1); a restored backup no longer chooses them. No AI consent changes.

To update from an installed 0.6 build to 1.0, install 1.0 by hand: a 0.6 build has no updater. From 1.0 on, use Check for updates.
